# 远程模式（进阶，规划中）

> **状态：还没实现。** 这份文档写的是设计思路和适用范围，
> 主线（本地启动）跑通之后再做。

## 想解决什么

笔记本显存有限（常见 8 GB），跑不了大模型。但家里/公司可能有一台
显存更大的机器。远程模式想做的事是：**在笔记本上照常使用客户端，
把推理请求转发到那台大机器上**。

这样客户端配置不用改，写作业的地方还是这台笔记本。

## 为什么不能简单开个端口

把 `llama-server` 监听到 `0.0.0.0` 再把端口映射出去，等于把推理服务
暴露在公网上。而 `llama-server` 默认**没有鉴权**，任何人都能用你的显卡
（顺便看你的提示词）。

所以远程模式必须解决三件事：

1. **不可公网直达** —— 用 Tailscale/WireGuard 这类打洞 VPN，
   设备之间点对点加密，不经过公网端口
2. **要有鉴权** —— `llama-server` 支持 `--api-key`，开了就必须带 key
3. **本地要有代理** —— 笔记本电脑上跑一个小转发，
   把 `127.0.0.1:1234` 的请求送到对端，客户端感知不到

## 打算怎么做

```
[客户端] → 127.0.0.1:1234 (本地转发)
                ↓ Tailscale 加密隧道
           [大机器] llama-server --host <tailscale-ip> --api-key xxx
```

本地转发有两种实现，各有取舍：

**A. `llama-server` 自带的 `--host`**（最简单）
在大机器上把 `--host` 设成 Tailscale 的 IP，笔记本直接连那个地址。
缺点：客户端要改地址，换网络时 IP 会变。

**B. 本地小转发脚本**
笔记本上跑一个几十行的 PowerShell，监听 `127.0.0.1:1234`，
把请求转发到对端。客户端完全不用改。
缺点：多一层，要处理流式响应（SSE）的透传。

倾向于做 B，因为「客户端零配置」是这个功能的意义所在。

## 需要额外注意的

- **API key 不能硬编码在脚本里**。存同目录的 sidecar 文件，
  首次运行生成随机 key，或者让用户填进 `config.ps1`（该文件已在 `.gitignore`）
- **对端的 IP 不要写死**。Tailscale 的 IP 会变，
  启动时用 `tailscale ip -4` 现取，取不到再退回配置里的值
- **首次连接要确认是 encrypted**。`tailscale status` 里看 `direct`，
  走 `relay` 也能用但延迟高
- **超时要设**。对端关机时本地转发不能一直挂着，
  否则客户端看起来像卡死

## 什么时候做

主线稳定、有人真的需要这个功能之后。现在的优先级是让本地启动足够可靠 ——
远程模式是锦上添花，本地启动是基本盘。
